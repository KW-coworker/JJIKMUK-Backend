# 2026-11-09 상품 전달본 수동 적용

이 도구는 사용자가 승인한 한 번의 상품 데이터 반영용이다. main 병합만으로 DB 변경이 실행되지 않는다. `server-maintenance.yml`의 `catalog` 모드에 고정 main SHA·새 request ID·승인된 source plan SHA를 지정해야 한다.

## 적용 범위

기존 상품 ID·바코드와 공통 42개 항목을 대조한 뒤, 제공받은 알레르기 근거·신뢰도를 반영하고 비어 있는 영양 기준량·사진을 보충한다. 기존 사진과 무관한 상품 필드는 보존한다. V21은 전달본의 이미지 역할·안내·해시·작업 ID 네 nullable 컬럼만 추가하며 V1~V20은 그대로 둔다. 기존 FULLTEXT 인덱스도 보존한다.

SOURCE_INGREDIENTS는 원문 보존 대상이다. 이를 안전 판정의 검증된 근거로 승격하는 변경은 포함하지 않는다. 새 사진 역할을 앱에서 표시하는 API·화면 연결도 별도 작업이다.

## 실행 순서

1. 승인된 상품 전용 비공개 S3 파일의 버전·크기·SHA와 main 원본 JAR를 고정한다. 회원 정보나 전체 덤프는 이 파일에 포함하지 않는다.
2. 기존 CD 유지보수 게이트를 닫고 진행 중인 서버 명령 종료를 기다린다. 고정 서버 점검 후 백엔드·챗봇을 중지하고 전체 보존 지문과 변경 전 값을 기록한다.
3. 동결 이후 암호화된 RDS 스냅샷이 사용 가능해진 것을 확인한다.
4. 같은 승인 job의 다음 단계에서 새 OIDC 세션을 받아 원본 V21을 적용한다. 상품은 500행씩 트랜잭션으로 갱신하며 변경 전 기록을 먼저 디스크에 보존한다.
5. 전체 상품·보존 필드·기존 이력·검색 인덱스를 검증한다. 원래 백엔드 함수로 새 관측 이력을 추가하고 사진이 바뀐 상품의 그룹 키만 갱신한다.
6. 같은 main 원본 JAR로 백엔드를 시작하고 기존 챗봇의 실행 설정·안정성과 무료 health 검사를 확인한다. 성공한 수동 DB 구조를 CD 기준에 등록한다.
7. 유지보수 제어기가 작업 중 바뀐 최신 main을 확인·배포한 뒤 CD를 재개한다. 실패 시 CD는 계속 보류한다.

## 실패와 복구

실패 기록을 지우거나 같은 request를 재실행하지 않는다. 같은 승인 job의 recovery 단계가 새 인증을 받고 정확히 기록된 작업만 확인한다. DB 변경 전 실패라면 상품 파일·공간 감시가 불가능해도 기존 서비스를 복귀할 수 있다. 데이터 복구 쓰기는 정상 공간 감시·lease·전체 원본 대조가 있을 때만 실행한다.

불확실한 commit은 실제 DB 값과 관측 이력으로 구분한다. 변경 전 상품값으로 돌아가되 복구 관측을 추가해 과거 이력을 보존한다. V21 적용이 완료됐다면 nullable 컬럼과 Flyway 이력을 남기고 V21과 호환되는 원본 JAR를 사용한다. DDL 부분 실패·알 수 없는 외부 변경은 자동 repair·컬럼 삭제·스냅샷 전체 복원으로 우회하지 않는다.

코드·데이터 파일은 서버의 전용 폴더에 분리하고 비공개 변경 전 기록은 서버에 보존한다. 공개 GitHub 로그에는 행 원문·이미지 URL·비밀값 대신 상태·건수·해시만 남긴다.

## 검증과 한계

실제 전달본을 별도 로컬 MySQL에 복원해 적용·복구를 시험한다. 저장 전/후 응답 유실, 복구 후 응답 유실, 변경 전 기록 변조에 대한 실패 주입 검사를 포함한다. 로컬 성공은 운영 성공이 아니며, 실제 실행은 별도의 결과와 최종 health·CD 상태 확인으로 완료 판정한다.

상품 파일 업로드가 승인·완료돼 정확한 S3 버전이 정해지기 전에는 source plan을 확정하거나 운영 실행하지 않는다. 이 도구는 새로운 IAM 권한, CloudShell 입력 또는 관리자 자격 증명을 요구하지 않는다. 기존 연결의 실제 거절·상태 불일치가 발생하면 원인을 보고하고 기록을 보존한다.
