# V21 상태에서의 상품 자료 재적용

이 코드는 새 실행을 준비한다. 운영 상품의 최종 반영 완료를 뜻하지 않는다. 기존 상품은 복구됐으며 백엔드가 정상이다. 사용자의 최소 여유 공간 2GiB 지시를 반영했으며 실행 직전 조건 검증이 남아 있다.

## 고정된 대상

- 기존 기관 RDS `jjikmuk-dev-db`, 백엔드 EC2, 동일 비공개 상품 원본의 S3 객체 버전만 사용한다.
- 유지보수 요청 `a5291163ee0a456b85366e6075d8fce6`의 CD 보류를 유지한다.
- 과거 실행 `42942707829`, 서비스 복구 `42953603757`의 결과·원본 state·저널 해시를 대조한다.
- 서비스 복구 후 등록된 main `70dc1a70fff94dd0bee30f34638a15add23c0f26`이 이전 릴리스다. 새 배포는 검토·병합된 main 원본으로 빌드한다.
- 이미 적용된 V1~V21은 변경하거나 다시 실행하지 않는다. V21 스키마 고정 해시와 이미지 컬럼 문자셋·정렬 규칙을 확인한다.

## 새 실행 순서

1. 현재 CD 보류 소유자와 서비스 복구 증거를 확인한다. RDS가 `available`, gp3, 20~40GiB이며 대기 중인 설정 변경이 없고 최근 여유 공간이 8GiB 이상인지 확인한다. 맞지 않으면 서비스 중단 전 멈춘다.
2. 새 main JAR·코드 묶음, 새 실행 ID·dataset·작업 폴더·변경 전 저널을 생성한다. 기존 상품 원본 파일은 해시를 확인한 읽기 전용 hardlink로 재사용한다. 원본 실행이나 저널을 수정해 재실행하지 않는다.
3. CD 보류를 새 실행에 조건부 연결한다. `OPEN`으로 풀었다가 다시 잠그는 과정은 없다.
4. 백엔드·챗봇 서비스를 중지하고 기존 저널에 기록된 상품 원복 값·관측 이력 연결 및 비대상 상품을 전수 재대조한다. 별도로 이번 실행 시점의 회원·로그 등 기존 자료와 변경 전 상품 값을 보존한다.
5. 새 암호화 RDS 스냅샷이 사용 가능한지 확인한다. 원본 V21 아래에서 승인된 상품 필드만 적용하고 관측 이력을 추가한다. 새 DB 테이블 설계나 알레르기 안전 판정 규칙을 만들지 않는다.
6. 상품 전수 비교, 이전 자료 보존, FULLTEXT 검색, 원본 main JAR와 챗봇 정상 상태를 확인한다. 완료 시 최신 main 반영과 최종 검증을 거친 뒤 기존 controller가 CD를 재개한다.

## 중단·복구

V21에서는 스키마가 같더라도 상품 값은 이미 달라질 수 있다. 따라서 `PRODUCT_APPLY_INTENT` 이후의 실패는 스키마 동일성만으로 복구를 생략하지 않는다. 새 변경 전 저널과 실제 DB를 비교해 원래 값을 복구하고, 원래 관측 이력에 이어 복구 이력을 남긴다. 이전 V21 호환 릴리스로 서비스를 복귀한다.

DB 쓰기 전 실패는 상품 변경 없이 기존 서비스를 복귀한다. 성공한 실행·진행 여부가 불명확한 쓰기·이미 소비된 복구를 자동 반복하지 않는다. 실패하면 CD 보류와 모든 기록을 유지한다. 후속 검증 실패는 성공으로 표시하지 않는다.

## 공간과 시간

| 경계 | 준비한 제한 |
|---|---|
| RDS 시작 여유 | 최소 8GiB |
| 적용 중 RDS 하한 | 5GiB: 최종 여유 2GiB + 복구 작업 공간 3GiB |
| 복구 중 RDS 하한 | 2GiB |
| 호스트 시작/작업 중 여유 | 5GiB / 2GiB |
| 호스트 동결/적용/복구 | 1,200 / 7,200 / 7,200초 |
| runner 절대 예산 | 3,000 / 8,500 / 8,700초 |
| GitHub job / 로컬 controller | 360분 / 약 400분 polling 상한 |

시간은 예상 완료 시간이 아니라 중단 상한이다. 명령을 보내기 직전에 준비·대기 시간을 뺀 잔여 시간을 검사하며, 적용 이후 점검과 스냅샷 확인에 필요한 시간도 미리 남긴다. GitHub 빌드 단계는 15분 상한이다.

같은 GitHub 실행의 OIDC로 동일 역할 자격을 메모리에서 갱신한다. 장기 AWS 클라이언트는 같은 갱신 세션을 공유하고, 매 서명과 Monitor에서 절대 종료 시각을 검사한다. 갱신은 실행 예산이나 권한 범위를 늘리지 않는다. 비밀값은 로그·파일로 내보내지 않는다.

호스트 S3 heartbeat 읽기는 지정된 일시적 전송 오류에만 최대 2회 시도한다. 권한·STOP·만료·공간·내용 오류는 재시도하지 않는다. SQL이나 SendCommand 재시도가 아니다.

## 검증 범위

Windows 운영 검사, Linux 상품 관련 검사, CD 회귀 검사 및 조건 반전 검사를 수행한다. 로컬 MySQL 8.4.11의 별도 2,000상품 DB에서 1,151건 실제 적용 후 새 V21 복구 분기로 모두 복원했고, 전수 상품 대조와 구조 불변을 확인했다. 이 로컬 검증의 서비스 시작·중지는 모의 동작이므로 운영 서비스 정상 검증을 대체하지 않는다.

빌드용 로컬 JAR와 기존 해시 고정 wheel로 실제 패키지를 구성해 신규 모듈 포함·격리 import도 검사한다. 실제 서버 적용과 최종 검증은 별도 실행 결과로만 확정한다.

사용자가 2026-11-11 최소 여유 공간을 2GB로 줄이고 적용 진행을 명시했다. 2GiB(2,147,483,648바이트)를 하한으로 사용한다. 앞선 30GiB 확대 요청은 철회하며 이 코드는 RDS 크기나 IAM 권한을 바꾸지 않는다.

시작 여유 8GiB는 최종 여유 2GiB + 적용 3GiB + 복구 3GiB다. 로컬 전체 적용·복구 후 물리 파일 증가 5,498,732,544바이트(약 5.12GiB, 앞선 부분 시도 포함)를 근거로 작업 합계 6GiB를 남긴다. 실제 증가량은 보장할 수 없어 최신 지표와 실행 중 하한 검사를 계속한다. 5GiB에 닿으면 적용을 멈추고, 복구는 별도 2GiB 하한을 사용한다. 이전 변경·복구 이력을 삭제해 공간을 만들지 않는다.

이미 소비된 원본 계획의 5GiB 값과 SHA-256은 보존한다. 새 실행 binding에 원본 값과 사용자 2GiB 승인 정책을 별도로 기록한다. 공용 Monitor/Guard의 기본 5GiB 기준은 그대로이며 이 재적용 경로만 명시적으로 2GiB 정책을 전달한다.
