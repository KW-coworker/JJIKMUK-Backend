# 상품 배치 임시표의 누적 읽기 보완

상품 적용이 후반으로 갈수록 느려졌다. 운영의 제한된 8초 관측에서 배치 임시표 DELETE가 5초, 배치 대조가 4초 동안 실행 중이었다. 그 관측에서 UPDATE 실행 계획은 얻지 못했으므로 운영 지연 전체의 단일 원인으로 단정하지 않는다.

로컬 MySQL 8.4.11에서 실제 전달본의 서로 다른 상품 ID를 500개씩 증가시키며 2,201회 넣고 지우자, DELETE의 논리 읽기가 100번째 3,208회에서 2,200번째 42,694회로 증가했다. 마지막 DELETE는 약 0.486초, 전체 실험은 195.7초였다. 같은 ID만 재사용한 이전 실험으로는 이 증가를 발견하지 못했다.

적용과 복구는 각 상품 트랜잭션의 BEGIN 전에 이 세션의 임시표를 DROP TEMPORARY/CREATE TEMPORARY로 새로 준비한다. 기본키를 CREATE 문에 정의하여 ALTER나 TRUNCATE를 사용하지 않는다. 상품·이력 테이블, 500행 상한, 원본 저장 저널, commit 불확실성 검사와 복구 기준은 유지한다. 초기화 오류는 즉시 전파되며 재연결하지 않는다.

MySQL의 [implicit commit 문서](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)에 따르면 TEMPORARY를 명시한 CREATE/DROP은 트랜잭션을 암묵적으로 확정하지 않는다. 임시표 생성·삭제 자체는 rollback 대상이 아니지만, 임시표는 상품 트랜잭션 전에 준비하며 실패한 작업은 계속 진행하지 않는다.

같은 110만 건 로컬 실험에서 새 준비 방식은 7.94초였고, 마지막 준비는 약 0.0003초였다. 이는 임시표 반복 실험 결과이며 운영 전체 작업의 예상 완료 시간은 아니다. 별도 로컬 DB에서 2,000개 상품 중 1,151개 적용과 원상복구를 검증했다. snapshot INSERT 직후·상품 UPDATE 직후·commit 응답 불명·복구 commit 응답 불명·훼손된 원본 저널의 실패 주입도 확인했다.

이 변경은 이미 실행 중인 패키지를 교체하지 않는다. 다음 실행은 현재 작업의 복구 결과, 보존된 저널, 저장공간, 고정 main을 확인한 별도 실행 계획으로 시작한다.
