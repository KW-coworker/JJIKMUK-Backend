# 백엔드 main 자동 배포 흐름

초기 설치·전환 검증이 끝나고 저장소 변수 `BACKEND_CD_ENABLED=true`일 때 다음 흐름으로 동작한다. DB 정비·초기 설치 workflow와 일반 main 자동 배포는 분리되어 있다.

1. PR의 필수 CI가 통과한 코드를 main에 병합한다. 리뷰 인원 설정은 0명이며, CD가 별도 팀원의 승인을 요구하지 않는다.
2. GitHub Actions `Backend CD`가 해당 main 원본을 테스트하고 JAR를 빌드한다. 배포 직전 확인에서 더 새로운 main이 발견되면 오래된 실행은 배포하지 않는다.
3. 백업 상태·기존 실행 파일과 환경·DB 변경 이력·새 JAR의 SQL 및 설정 호환성을 자동 검사한다. DB 변경이 필요한 배포는 거절한다.
4. 검사를 통과하면 기존 EC2의 백엔드 JAR 경로를 바꾸고 재시작한다. 같은 새 프로세스에서 상태 API와 DB 검사가 60초 연속 정상이어야 성공이다.
5. 배포 후 검사에 실패하면 호환성을 확인한 기존 정상 JAR로 복귀한다. 설정이나 DB가 예상과 달라 복귀도 안전하게 확인할 수 없으면 추가 배포를 차단한다.

일반 자동 배포는 `backend-production` 환경을 사용하며 사용자나 Codex의 승인 클릭이 없다. 관리 작업·초기 설치용 `production` 환경의 승인 설정은 별도다. 입력 없는 수동 `Backend CD` 실행은 테스트·빌드만 수행한다. 검증된 수동 작업 ID를 전달한 재개 실행만 서버 반영을 허용한다.

## 자동 배포에 포함되지 않는 작업

- DB 구조 변경·상품 데이터 병합은 요청받아 원본 SQL과 검증·복구 기준을 확인한 뒤 따로 수행한다.
- OCR 모델·서버 코드와 Python 챗봇 프로그램은 이 백엔드 JAR 교체로 바뀌지 않는다.
- 개발자 AI 일괄 허용과 기존 운영 환경파일은 유지한다. 상태 검증에서 유료 AI를 호출하거나 사용자 채팅을 생성하지 않는다.

## 실패를 확인하는 곳

GitHub Actions의 `Backend CD` 실행과 결과 요약을 확인한다. 실패 알림 workflow는 고정된 오류 분류를 바탕으로 이유·실행 링크·다음 조치를 안내한다. LLM API를 호출하지 않는다. PR 작성자는 알림과 실행 결과를 확인하고 수정 PR을 병합한다. 원인 미확인 상태에서 같은 명령이나 설치 작업을 재실행하지 않는다.

새 기능의 모든 업무 동작을 자동 검사가 보증하는 것은 아니다. APK의 주요 화면과 기능은 담당자의 기능 시험도 필요하다.

## DB·OCR 작업과 겹치지 않게 관리하기

승인된 DB·OCR 작업은 [수동 배포 연계 자동화](../operations/MAINTENANCE_CD.md)를 사용한다. 같은 작업 그룹에서 기존 배포가 끝나길 기다리고, 지속되는 중단 상태를 기록한 뒤 작업·검증을 수행한다. 현재 main 반영과 서버의 새 검증까지 끝나야 일반 CD를 재개한다. 실패나 실행기 종료만으로 중단 상태를 해제하지 않는다.

## 자동 배포를 멈추려면

저장소 **Settings → Secrets and variables → Actions → Variables → `BACKEND_CD_ENABLED`**를 `false`로 바꾼다. 이후 배포 실행을 막는 설정이며, 이미 전환 중인 서버 작업을 즉시 취소하거나 기존 버전으로 돌리는 기능은 아니다. 진행 중인 작업은 먼저 실행 기록과 복귀 결과를 확인한다.
