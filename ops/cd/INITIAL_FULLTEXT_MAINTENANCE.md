# 최초 DB 구조 준비

2026-11-10 실행 `42798585519`는 동결·원본 지문 기록·스냅샷 준비 후 AWS 연결 종료 오류로 DB 변경 전에 중단했고, 기존 두 서비스가 복귀했다. 기존 실행·스냅샷·호스트 기록은 보존한다. 새 요청은 그 정확한 이전 기록이 `FROZEN_NO_DB_WRITES`에서 복귀했고 DDL 기록이 없음을 확인한 뒤 별도 `jjikmuk-backend-initial-db-receipt-20261110` 폴더에서 다시 동결·백업한다.

실행 기록을 S3에 저장하다 응답을 잃으면 같은 내용과 이번 호출에서만 생성한 무작위 표식을 조회해 확인한다. 다른 실행의 표식이거나 표식이 없는 기존 기록은 내용이 같아도 거절한다. 아직 없거나 조회 연결이 끊겼을 때만 같은 `If-None-Match: *` 조건부 기록 저장을 최대 3회로 제한한다. 최초 요청부터 기존 기록이 있으면 여전히 재실행을 거부한다. 이 처리로 스냅샷 생성·SSM 명령·SQL을 재전송하지 않는다. 근거: [S3 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [일관성](https://aws.amazon.com/s3/consistency/).

원본 V17의 INSTANT 컬럼 추가는 운영 products의 기존 FULLTEXT 구조와 충돌한다. SQL·체크섬·업무 데이터를 고치지 않고, 승인된 운영 정비 후 원본 V17~V20을 적용한다. 일반 검색은 기존 search_keywords/ngram 인덱스로 복원한다.

`backend-initial-db.yml`은 CD가 비활성인 정확한 main에서만 실행한다. 같은 요청의 재실행은 금지하며 S3 실행 의도와 호스트 상태 파일을 보존한다.

1. **동결:** 원본 JAR·환경·인증서·DB 구조·프로젝트 스키마 관측 권한·검색·여유 공간을 확인하고, 서비스 정지 전에 `jjikmuk`의 활성 예약 이벤트가 없는지 검사한다. 백엔드와 기존 챗봇을 정지한 뒤 같은 DB 계정의 나머지 연결이 종료될 때까지 최대 30초 기다린다. 그 시점의 원본 컬럼·행·변경 이력 지문을 비공개 파일에 기록한다.
2. **백업:** 동결 이후 생성한 암호화 RDS 수동 스냅샷이 사용 가능해질 때까지 확인한다. 실패하면 DB 변경 없이 기존 서비스를 복귀한다.
3. **정비:** 스냅샷 대기 중 데이터·구조 변화가 없음을 다시 검사한다. 기존 FULLTEXT 제거, products 물리 재구성, 같은 main JAR의 Flyway/ConnectorJ로 원본 V17~V20 적용, 동일 FULLTEXT 복원을 수행한다.
4. **검증·복귀:** 기존 컬럼/행/인덱스/FK/테이블 옵션/트리거/검색 결과와 V1~V20 이력을 검사한다. 성공한 뒤 동일한 기존 JAR과 챗봇을 재가동하고 무료 상태 점검을 수행한다. 이 작업이 새 백엔드 JAR 배포나 자동 CD 활성화를 의미하지는 않는다.

GitHub가 기존 연결로 FreeStorageSpace를 읽어 20초마다 비공개 S3 감시 기록을 갱신한다. 호스트는 기존 EC2 역할로 이를 확인하며 최소 5GiB, 기록·관측 시각, 요청·아카이브 바인딩을 검사한다. DB 관측용 SDK는 고정 해시의 별도 폴더에서 실행하며 기존 Python 환경에 설치하지 않는다.

### 2026-11-10 사용자 확인에 따른 프로젝트 범위

사용자는 서버 변경을 혼자 관리하고 DB 담당자가 운영 DB에 직접 접속하지 않으며, 앱에 주기 작업이 없는 것으로 알고 있다고 확인했다. 이 정비는 해당 단독 운영 조건과 작업 중 다른 배포·DB 수정을 하지 않는 조건을 사용한다. 전체 MySQL 사용자·트랜잭션·다른 스키마의 이벤트를 전부 관측했다는 주장은 하지 않는다.

`jjikmuk.*`의 TRIGGER/EVENT 권한으로 프로젝트 메타데이터를 확인한다. 전역 PROCESS/TRIGGER/EVENT나 IAM·DB 추가 권한을 요구하지 않는다. 같은 계정의 연결은 기본 DB가 달라도 확인하며, 발견한 연결을 임의로 끊지 않고 정비를 중단한다. 프로젝트의 활성 이벤트도 임의로 끄지 않고 서비스 정지 전에 거절한다.

MySQL 메타데이터 잠금은 개별 DDL의 일관성을 보호하지만 정비 전 구간의 전역 쓰기 차단 장치는 아니다. 미신고 계정·다른 스키마 이벤트의 쓰기는 이 범위 밖이다. 기존 원본 데이터 지문을 백업 후와 정비 후 대조하여 변화를 발견하면 후속 단계를 중단하고 기존 부분 적용 복구 기준을 따른다. 동일 계정 세션 관측·취소 및 원본 SQL 적용은 전역 PROCESS 없는 격리 MySQL 계정으로 검증한다.

### 서비스 종료 상태 보완

run42795881275는 서비스 정지 확인에서 중단됐고 고정 복귀 명령이 기존 서비스 정상 복귀를 검증했다. 스냅샷·DB DDL은 실행하지 않았다. systemd는 실제 프로세스가 종료됐어도 종료 코드에 따라 `failed/failed`를 남길 수 있다. 로컬 격리 서비스의 SIGTERM→exit143으로 이 조건을 재현했으며, 운영 실행도 같은 종료 코드였다는 주장은 하지 않는다.

종료 판정은 `inactive/dead` 또는 `failed/failed`와 함께 MainPID·ControlPID 0, 대기 Job 없음, 전체 cgroup 프로세스 없음, 전후 상태 일치를 확인한다. 운영 unit의 SuccessExitStatus·Restart 설정을 바꾸거나 reset-failed를 실행하지 않는다. 새 실행은 이전 기록의 정확한 요청/커밋, DB 쓰기 전 정상 복귀 상태, 작업 목록·스냅샷·동결 결과 부재와 기존 앱 입력을 확인한 뒤 별도 `...initial-db-stop-proof-20261110` 기록을 사용한다. 이전 폴더·파일은 그대로 보존한다.

작업 중 감시 중단·공간 부족·시간 초과가 발생하면 이후 단계로 넘어가지 않는다. 직접 DDL의 연결 ID 및 Flyway가 SQL 실행 전에 기록한 연결 ID만 대상으로 종료를 요청하고 서버에서 종료 여부를 확인한다. 취소 요청의 응답을 잃어도 같은 요청을 무작정 다시 보내지 않는다. 다른 사용자의 연결은 종료하지 않는다.

MySQL DDL은 자동 커밋되므로 전체 SQL 자동 롤백을 약속하지 않는다. DB 변경 전이거나 보존 검증까지 완료된 상태만 자동 서비스 복귀가 가능하다. 부분 적용·종료 불명확·복귀 검증 실패는 기록을 보존하고 후속 점검한다. 스냅샷 복원은 기존 DB를 덮어쓰지 않으며 별도의 검토된 복구 경로가 필요하다.

단계 시작 전에 1시간 역할 인증의 남은 시간을 보수적으로 계산한다. 정비 시작은 종료 관측과 서비스 복귀를 위한 여유까지 남았을 때만 허용한다. 스냅샷 대기 중 GitHub 실행기 자체가 강제 종료되면 호스트에서 자동으로 서비스를 재가동하지는 않는다. 이 경우 Codex가 기존 연결로 기록을 조회하고 고정 복귀 명령을 별도로 실행한다. 기록이나 잠금을 지워 최초 작업을 반복하지 않는다.

검증에는 실제 MySQL 8.4.11의 INSTANT 충돌 재현, 원본 SQL 적용, NULL·대소문자·바이너리 보존, 서버 세션 취소, Linux 자식 프로세스 종료, SDK 권한·변조 거절, 백업 실패 시 정비 미실행과 서비스 재가동 실패 시 재정지가 포함된다. 실서버 결과는 별도 실행 기록으로 확인한다.
