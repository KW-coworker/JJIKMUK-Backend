# 최초 백엔드 CD 전환

사용자가 승인한 DB 구조 준비와 CD 설치·배포·최종 검증 범위의 최초 전환이다. 반복 main 배포에 쓰는 일반 CD와 분리한다. DB 정비 완료 기록이 `DB_PREPARED`여야 하며, 기존 V1~V16과 설정을 유지하고 승인된 원본 V17~V20만 추가한 main JAR인지 검사한다.

1. 정확한 main에서 테스트·JAR 빌드 후 고정 AWS CLI 2.39.6·PyMySQL 1.2.3과 함께 포장한다. 해시와 main 일치가 다르면 설치하지 않는다.
2. 기존 GitHub OIDC 연결로 RDS 상태·자동 백업을 확인한다. 새 `/opt/jjikmuk-cd`, `/etc/jjikmuk-cd`, 공통 실행 기록 폴더에 CD를 꺼 둔 채 설치한다. 이 단계에서 앱을 재시작하지 않는다.
3. 호스트 안에서 기존 JDBC 주소를 읽어 CD 전용 비공개 설정에 넣는다. 비밀번호·주소 옵션 값은 GitHub 출력에 넣지 않는다. 기존 운영 환경파일은 그대로 사용한다.
4. `zzzzzzzzz-backend-cd-20261110.conf` 한 개로 JAR 경로만 CD의 `current/backend.jar`로 전환하고 백엔드를 재시작한다. 개발자 AI 일괄 허용, JVM 메모리, 작업 폴더는 유지한다. 챗봇·OCR 코드 및 DB는 변경하지 않는다.
5. 새 프로세스·파일 지문·환경·DB V1~V20 이력과 무료 상태 API 6개가 같은 프로세스에서 60초 연속 정상일 때 최초 정상 기준을 등록한다. 이 작업 자체는 GitHub 자동 CD 변수를 켜지 않는다.

후속 활성화는 이 성공 결과를 확인한 후 수행한다. 일반 main 자동 CD는 기존 테스트·빌드·배포 전 검사·상태 검사·실패 알림을 사용한다. DB 구조가 달라지는 변경은 자동으로 SQL을 실행하지 않고 배포를 거절한다.

## 실패와 복귀

전환 전에 거절되면 기존 앱을 유지한다. 전환 이후 실패하면 새 drop-in과 생성한 baseline을 보존 폴더로 옮기고, 기존 보호 파일·JAR·DB 호환성을 확인한 뒤 기존 JAR로 재시작한다. 새 프로세스로 60초 연속 정상임을 확인해야 복귀 성공으로 기록한다. 입력이 달라졌거나 복귀 검증이 실패하면 백엔드를 정지하고 추가 작업을 차단한다. DB 변경을 되돌린다는 의미는 아니다.

응답을 잃은 SSM 명령은 원래 명령을 조회·수집하며 재전송하지 않는다. 강제 종료 후 고정 복구는 정확한 설치 payload·커밋·JAR·기존 coordinator 상태에만 적용한다. 새로운 main이 생기면 신규 설치·전환은 거절하지만, 이미 시작한 고정 작업의 복귀는 막지 않는다. GitHub 실행기 전체가 사라지거나 복구 결과를 수집할 수 없으면 기존 연결로 기록부터 확인해야 하며 자동 복귀 완료라고 간주하지 않는다.

## 검증 범위

단위 검사에는 원본 SQL·설정 변경 거부, 전환 단계별 실패, 파일을 보존하는 복귀, 복귀 전 설정 변경 거부, 반복 재시작 및 제한시간 초과 거부, main 이동 후 복구, 설치 실패 시 앱 미전환이 포함된다. Linux에서는 실제 파일 쓰기·잠금·프로세스 종료 및 공식 도구의 임시 폴더 설치를 검증한다. 운영 고의 장애 주입·유료 AI·개인정보 쓰기는 수행하지 않는다. 실제 설치 성공과 최종 CD 작동은 별도 실행 결과로 확인한다.
