# 상품 동일성 용량 리뉴얼 구분 기준

기준일: 2026-10-28. 백엔드 후속 구현의 식별 기준을 정한다. **검색 카드 묶음, 구매 가능한 옵션, 원재료가 적용되는 제품 버전, 원본 데이터 행을 서로 다른 대상으로 관리한다.** 이름·제조사·이미지가 같다는 이유만으로 원본 자료를 병합하거나 안전 판정을 공유하지 않는다.

이 문서는 설계 기준이다. 현재 DB의 기본키·자료·기존 API 계약은 변경하지 않는다. 구현 전환 시 아래 수용 기준을 테스트하고 스테이징에서 검증한다. 이전 문서의 product_group_key를 영구 상품 ID로 사용하는 해석은 이 기준으로 대체한다.

2026-10-28 후속 구현: [관측 이력·내부 ID·용도 정책](catalog-evolution-stage1-3.md).
아래 현행 비교표는 설계 당시 상태이며, 후속 코드에서는 표시 그룹 키 ID 재사용을 제거하고 관측 이력을 추가했다.
이는 아래의 모든 group/variant/revision 모델 구현이나 실제 DB 적용 완료를 뜻하지 않는다.

## 1. 현재 코드와 새 기준의 차이

| 구분 | 현재 구현 | 확정한 후속 기준 |
|---|---|---|
| 기본 식별 | Product 엔티티의 @Id는 barcode | 실제 바코드와 내부 식별자를 분리한다. 누락 바코드를 행 번호로 영구 식별하지 않는다 |
| 검색 카드 묶음 | 상품명·제조사·원재료·이미지 URL로 product_group_key 생성 | 이 키는 임시 화면 중복 제거용이다. 영구 상품 동일성을 증명하지 않는다 |
| 용량 옵션 | 정규화한 총량·단위로 묶음 | 총량, 개별 용량, 개수, 포장 구조를 분리해서 보존한다 |
| 같은 총량 | 50g×2와 100g을 모두 g:100으로 묶음 | 내부 variant는 다르다. 화면의 총량 그룹과 내부 옵션을 분리한다 |
| 리뉴얼 | 동일 바코드 자료의 버전 구분 없음 | 확인된 상품 연속성이 있으면 같은 variant 아래 별도 revision으로 보존한다 |
| 무바코드 재적재 | 유일한 product_group_key 일치 등으로 기존 product_id 보존 | 출처 식별자·검수 매핑 기반으로 보존한다. 이미지 URL이나 CSV 행 번호에 의존하지 않는다 |
| 같은 용량의 충돌 자료 | 용량 API에서 보수적 합산 | 임시 방어는 유지하되, 실제 리뉴얼과 자료 오류를 구분한 뒤 revision별로 판정한다 |

현재 적재기는 중복 바코드의 첫 행을 유지하므로, 버전·출처 모델로 전환할 때는 중복 원본 행을 별도 보존하는 적재 경로가 필요하다. 이 문서 작성만으로 그 적재 동작이 바뀌지는 않는다.

## 2. 식별 대상과 이름

| 대상 | 논리 식별자 | 역할 | 변경 원칙 |
|---|---|---|---|
| 상품 그룹 | group_id | 같은 브랜드·기본 상품·맛·형태의 용량 옵션 묶음 | 다른 맛·기본 제품·명확한 다른 제형은 다른 그룹 |
| 판매 옵션 | variant_id | 용량과 포장 구성이 확정된 선택 대상 | 총량, 개별 용량, 개수, 포장 형태가 달라지면 다른 옵션 |
| 표시 정보 버전 | revision_id | 해당 옵션의 원재료·알레르기·영양·제조 근거 스냅샷 | 확인된 라벨/조성 변경은 새 버전 |
| 원본 자료 | source_record_id | 출처에서 수집한 원본 행과 증거 | 같은 출처 자료의 갱신도 이전 증거를 보존 |
| 바코드 연결 | barcode_binding_id | 바코드 문자열과 옵션·버전 후보의 연결 | 근거·유효기간·상태를 보존. 바코드 하나로 유일한 버전이라고 단정하지 않음 |

관계는 `group → variant → revision`이며 원본 자료와 바코드 연결이 이를 뒷받침한다. 이름과 이미지 URL은 이 식별자의 값이 아니고 변경 가능한 속성이다. 새 ID는 영구 발급하여 재사용하거나 CSV 재정렬에 따라 다시 만들지 않는다.

기존 `products.product_id`가 있는 환경에서는 현재 자료 행의 내부 ID로 우선 보존한다. 이를 검수 없이 새 variant_id/revision_id로 재해석하지 않는다. 현재 ID와 새 ID 사이의 명시적 매핑을 만든 뒤 소비자를 전환한다. 이 문서의 논리명은 추후 테이블 이름과 반드시 같아야 하는 것은 아니지만 의미는 유지한다.

## 3. 같은 상품 그룹으로 보는 기준

그룹 확인에 사용하는 요소는 검증된 브랜드/상품 소유자, 기본 제품명, 맛·향, 형태/제품 유형이다. 제조사 원문은 보존하되 제조원·판매원·브랜드 소유자를 같은 의미로 취급하지 않는다.

- 공백·대소문자·Unicode 정규화와 검수된 제조사 별칭은 표기 차이로 처리할 수 있다.
- 상품명의 맛, 무가당/제로, 유아용, 글루텐프리 등 제품을 구분하는 단어를 무조건 제거하지 않는다.
- 용량 표현은 **명확히 파싱된 경우에만** 그룹명에서 분리하고 원문을 남긴다. 모델명·기념 숫자를 용량으로 삭제하지 않는다.
- 동일 이름의 다른 브랜드는 다른 그룹이다. 브랜드·소유자가 불명확하면 제조사명 유사도만으로 합치지 않는다.
- 제조사/OEM 변경은 브랜드와 제품 연속성의 공식 근거가 있으면 같은 그룹을 유지할 수 있으나 검수가 필요하다. 근거 없는 법인명 치환은 하지 않는다.
- 이미지 URL, 사진 내용의 유사도, 카테고리 일치, 영양 수치 유사도는 후보 검색에만 사용하며 동일 상품의 결정 근거로 사용하지 않는다.
- 원재료가 다르더라도 확인된 리뉴얼은 같은 그룹일 수 있다. 반대로 원재료가 같다는 사실만으로 같은 상품이 되지는 않는다.

현재 값에 필요한 식별 요소가 없으면 provisional(임시 미확정) 상태로 보존한다. 빠진 값을 같다고 간주하지 않으며 자동 병합하지 않는다.

## 4. 용량과 포장 구성

다음 정보를 원문과 함께 분리해서 보존한다.

- total_quantity / quantity_unit: 총량. 질량은 g, 부피는 ml로 정규화한다.
- unit_quantity / unit_count: 개별 용량과 개수. 명시적인 근거가 있을 때만 채운다.
- package_kind: 봉지·병·캔·박스 등 확인된 판매 포장. 미상은 null이다.
- capacity_status: KNOWN / PARTIAL / UNKNOWN / CONFLICT.

`1kg = 1000g`, `1L = 1000ml`처럼 같은 차원 내 단위 변환은 가능하다. g와 ml는 밀도를 추정하여 서로 변환하지 않는다. 총량만 있으면 1개 포장이라고 임의 추정하지 않는다.

`50g×2`는 총량 100g·개별 50g·개수 2로 보존한다. `100g×1`과 다른 variant다. `100g`만 있는 자료는 포장 수가 미상일 수 있으므로 둘 중 하나로 자동 연결하지 않는다.

혼합 묶음의 `50g×2 + 30g×1`은 하나의 unit_quantity로 단순화하지 않는다. 구성 목록이 확인되지 않으면 검수 대상으로 남긴다. 총량과 묶음 계산이 충돌하면 CONFLICT이며 큰 값이나 더 그럴듯한 값을 임의 채택하지 않는다.

용량이 없는 모든 자료를 하나의 unknown 옵션으로 합치지 않는다. 동일성 근거가 없으면 별도 임시 옵션으로 보존한다. 용량 미상만으로 알레르기 DANGER가 되는 것은 아니며, 제품 식별의 불확실성과 성분 판정은 분리한다.

### 화면 표시와 내부 식별 분리

같은 원본 상품의 자료 행이 늘었다는 이유로 옵션을 늘리지 않는다. 화면에서는 총량별 상위 그룹을 유지할 수 있지만, 같은 총량에 다른 판매 구성이 확인되면 `100g 1개` / `50g 2개`와 같이 구별 가능한 선택이 필요하다.

프론트가 그 선택을 아직 제공하지 못하면 대표 바코드 하나를 구매 옵션이라고 자동 확정하지 않는다. 집계 범위와 미확정 상태를 표시한다. 최종 선택은 이후 variant_id 및 필요 시 revision_id로 전달하며, 바코드는 보조 조회 키이다.

## 5. 리뉴얼과 자료 충돌

리뉴얼은 동일 상품·동일 판매 옵션이라는 연속성 근거가 있는 상태에서 실제 표시 정보가 바뀐 경우다. **문자열이 다르다는 사실은 변경 후보이지 리뉴얼 확정이 아니다.**

| 차이 | 처리 |
|---|---|
| 사진 URL, 촬영 각도, 디자인 색만 변경 | 같은 variant/revision. 이미지 자산 변경 이력만 보존 |
| 동일 근거의 띄어쓰기·OCR 오타 정정 | 같은 variant/revision. 정정 전후 값과 검수 이력 보존 |
| 100g → 90g | 같은 그룹의 새 variant. 이전 판매 옵션과 대체 관계를 별도 기록 |
| 원재료·알레르기 표시·실제 조성 변경 확인 | 같은 variant의 새 revision. 이전 자료를 덮어쓰지 않음 |
| 실제 제품의 영양 표시 변경 확인 | 같은 variant의 새 revision. 표시 기준/단위도 함께 보존 |
| 1봉 기준과 100g 기준의 수치 차이 | 우선 기준 단위 대조. 환산으로 일치하면 리뉴얼 근거로 쓰지 않음 |
| 자료마다 원재료가 다르지만 변경 시기·근거 없음 | CONFLICT. 시간 순서를 추정해 신·구형으로 확정하지 않음 |
| 다른 맛·제로 라인 등 별도 제품 | 다른 그룹. 단순 리뉴얼로 묶지 않음 |
| OEM·제조원 변경 | 공식 연속성 및 표시 자료 확인 후 새 revision 또는 별도 그룹을 검수 결정 |

출처 갱신일/수집일과 실제 적용 시작일을 분리한다. 최신으로 수집된 자료가 최신 제조 제품이라는 뜻은 아니다. revision의 적용 시점을 모르면 null로 두며 이전 버전이 유통 중일 가능성을 지우지 않는다.

### 같은 바코드에서 구형과 신형이 공존하는 경우

1. 바코드로 가능한 variant/revision 후보를 조회한다.
2. 제조일·포장 표기 등 검증 가능한 추가 정보로 버전을 좁힌다.
3. 하나로 확정하지 못하면 제품 식별 상태를 AMBIGUOUS로 둔다.
4. 영양 수치는 서로 섞거나 평균 내지 않는다. 특정 버전 값임을 표시한다.
5. 가능한 버전 중 등록 조건과 충돌하는 자료가 있으면 충돌 경고를 유지하고, 해당 실물의 버전 확인을 요청한다. 실제 실물에 성분이 확정됐다고 단정하지 않는다.
6. 충돌이 없더라도 정보 부족 또는 버전 식별 미완료 상태를 개인 맞춤 안심 추천으로 승격하지 않는다. 후면 라벨·바코드/제조 표기 추가 확인으로 연결한다.

상품 식별 상태(RESOLVED/AMBIGUOUS/UNRESOLVED)와 성분 판정(PASS/DANGER/UNKNOWN 등)은 별도 축으로 전달한다. 이는 후속 API 계약이며 현재 응답에 이미 구현된 필드가 아니다.

## 6. 바코드 없는 상품과 재적재

- 실제 바코드는 문자열로 보존하고 선행 0을 제거하지 않는다. 모든 값을 무조건 13자리 GTIN으로 변환하지 않는다.
- NO_BARCODE_ROW_*는 기존 API 호환 식별자이지 스캔 가능한 바코드가 아니다. 새 모델에서는 실제 barcode=null과 별도 legacy ID 매핑으로 분리한다.
- 출처의 안정적인 record key가 있으면 `(source, source_record_key)`와 이전 매핑을 이용한다. 품목보고번호 하나가 맛·용량까지 항상 식별한다는 가정은 금지한다.
- 안정적인 출처 키가 없으면 검수된 identity mapping을 사용한다. fingerprint는 후보 비교용이며 이름/이미지만의 일치로 영구 ID를 재사용하지 않는다.
- 매칭이 여러 개이거나 자료가 불충분하면 임시 자료로 보존하고 검수 대상으로 둔다. CSV 행 번호 변화만으로 다른 상품에 기존 이력·추천 ID를 붙이지 않는다.
- 동일 바코드의 여러 행을 단순 첫 행 우선으로 버리지 않는다. 원본 행은 보존한 뒤 동일 자료/별도 버전/출처 충돌을 분류한다.
- 영양값·원재료·이미지를 여러 자료에서 조합할 때 각 필드의 출처와 기준 버전을 보존한다. 같은 revision이라는 확인 없이 합성 라벨을 만들지 않는다.

## 7. 자동 연결과 검수 결과

다음은 매칭 작업의 결과 코드이며, 높은 유사도 자체를 승인으로 취급하지 않는다.

| 결과 | 허용 조건/동작 |
|---|---|
| SAME_REVISION | 승인된 기존 매핑 또는 안정적인 출처 연결로 동일 옵션·동일 표시 버전이 확인됨. 새 관측 자료만 연결 |
| NEW_VARIANT | 상품 그룹의 연속성이 확인되고 용량·포장 구성이 다름. 새 variant 발급 |
| NEW_REVISION | 동일 옵션의 실제 표시 변경이 확인됨. 새 revision과 근거 기록 |
| NEW_GROUP | 브랜드·기본 제품·맛·형태가 다른 것으로 확인됨 |
| REVIEW_REQUIRED | 원재료 충돌, 포장 미상, 제조원 역할 불명, 바코드 다중 후보 등. 자동 병합 금지 |
| UNRESOLVED | 비교할 충분한 근거 없음. 원본 및 임시 ID 보존 |

원본 데이터 행을 삭제해서 중복을 해결하지 않는다. 승인된 연결/병합/분리에는 결정 사유, 검수자, 시각, 규칙 버전, 이전/이후 매핑을 남기고 되돌릴 수 있어야 한다.

## 8. 후속 구현 및 전환 순서

1. 로컬 복사본에서 중복 바코드·용량 누락·묶음·원재료 충돌 표본을 추출한다. 원본 전체 파일 검토와 DB 집계는 별도 작업이다.
2. 위 규칙으로 사람이 검수한 매핑 정답을 만든다. 현재 표시 그룹 키와 새 동일성 결과의 차이를 기록한다.
3. 기존 products를 유지하고 그룹/옵션/버전/출처/바코드 연결과 legacy 매핑 구조를 추가한다. 기존 product_id 숫자는 보존한다.
4. 스테이징 적재에서 기존 승인 매핑을 재사용하고 신규·충돌·미확정을 분리한다. 실제 바코드 연결과 합성 legacy ID는 별도로 검사한다.
5. 상품 검색·상세·옵션·추천·챗봇에 같은 resolved identity와 판정 범위를 전달한다. 현재 BARCODE_ROW와 CAPACITY_GROUP 차이는 자동으로 해소됐다고 가정하지 않는다.
6. 이력은 당시 선택한 variant/revision 및 판정 버전을 보존한다. 기존 바코드 이력에서 버전을 알 수 없으면 미확정으로 유지하며 과거를 최신 버전으로 소급 연결하지 않는다.
7. 사전 추천 후보·캐시의 데이터 버전을 연동하고 리뉴얼 후에도 현재 제약을 다시 평가한다. 영구 ID가 같다는 이유만으로 이전 판정을 재사용하지 않는다.
8. API 호환 매핑, 정답셋, 재적재/롤백을 검증한 뒤 명시적인 승인 하에 소비자 참조와 기본키를 단계적으로 전환한다. 운영 DB 작업은 별도 승인 대상이다.

## 9. 수용 테스트 목록

| 번호 | 입력/변경 | 기대 결과 |
|---|---|---|
| I01 | 동일 근거의 공백·대소문자 차이 | 같은 그룹/옵션/버전 유지 |
| I02 | 이미지 URL 또는 사진만 변경 | 모든 영구 상품 ID 유지 |
| I03 | 같은 이름, 다른 브랜드 | 다른 그룹 |
| I04 | 같은 브랜드, 다른 맛 | 다른 그룹 |
| I05 | 같은 제품, 1kg와 1000g, 동일 포장 확인 | 같은 variant |
| I06 | 같은 제품, 1L와 1000ml, 동일 포장 확인 | 같은 variant |
| I07 | 100g와 100ml | 단위 차원 불일치, 자동 동일 옵션 처리 금지 |
| I08 | 100g 1개와 50g 2개 | 같은 그룹의 다른 variant |
| I09 | 총량 100g만 있음, 포장 미상 | 알려진 두 구성 중 임의 연결 금지 |
| I10 | 서로 다른 용량 미상 자료 | 결측값만으로 합치지 않음 |
| I11 | 총량과 묶음 계산 불일치 | CONFLICT, 검수 |
| I12 | 같은 바코드, 원재료 변경과 적용 근거 있음 | 같은 옵션 새 revision, 구형 보존 |
| I13 | 같은 바코드, 원재료 불일치와 시점 근거 없음 | CONFLICT/REVIEW_REQUIRED |
| I14 | 같은 바코드의 구형·신형, 알레르기 상이 | 버전 미확정 상태·충돌 경고 유지, 추가 확인 |
| I15 | 수집일만 최신 | 제조 버전 최신이라고 확정하지 않음 |
| I16 | 100g에서 90g으로 변경 | 새 variant, 이전 옵션 보존 |
| I17 | 표시 단위가 다른 영양값 | 단위 대조 전 리뉴얼 판정 금지 |
| I18 | CSV 정렬/이미지 변경 후 재적재 | 승인된 identity mapping의 영구 ID 유지 |
| I19 | 같은 품목보고번호의 여러 용량 | 번호만으로 하나의 variant로 합치지 않음 |
| I20 | 잘못된 병합 발견 후 롤백 | 원본과 이전 매핑·이력 복구 가능 |
| I21 | 동일 상품/옵션/버전/프로필을 상세·추천·챗봇에 전달 | 같은 판정 근거와 범위 유지 |
| I22 | 과거 이력의 버전 미상 | 최신 revision으로 임의 소급 연결하지 않음 |

이 목록은 후속 구현의 검증 기준이며 현재 실행을 완료한 자동 테스트 목록이 아니다.

## 10. 팀 합의가 필요한 표시 방식

백엔드 기준은 위와 같이 고정한다. 프론트·AI 담당자와는 다음 전달/표시 방식을 확정한다.

- 총량이 같고 포장이 다른 경우 2차 옵션을 표시할지, 상품 카드 자체를 구분할지. 내부 구분을 없애는 방식은 사용하지 않는다.
- 리뉴얼 버전이 불명확할 때 어떤 후면 라벨·제조 표기를 추가로 요청할지와 OCR 담당자의 추출 항목.
- variant/revision 식별자 추가 시 기존 barcode API를 유지할 기간과 클라이언트 전환 일정.
- 그룹·리뉴얼 연결을 최종 승인할 담당자와 근거 저장 위치.

정확도 수치, 자동 병합 유사도 임계값, 새 DB 스키마 배포일은 이번 기준만으로 정하지 않는다. 실제 표본 검수와 전환 리허설 후 결정한다.
